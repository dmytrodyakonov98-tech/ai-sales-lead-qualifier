# M001-B001 First Deterministic Vertical Design

## Status

Approved and frozen on 2026-09-02.

## Goal

Prove one fixed inbound lead can move through the canonical AI Sales Lead
Qualifier flow to `AWAITING_HUMAN_APPROVAL` with zero destination side
effects, then—only after approval bound to the exact candidate hash—create one
built-in CRM record, materialize `lead_decision_bundle_v1`, persist evidence,
restart, and independently verify the same result.

## Exact vertical

```text
LOCAL FORM
→ NORMALIZE
→ EXTRACT
→ QUALIFY
→ SCORE
→ EXPLAIN WHY
→ NEXT ACTION
→ RESPONSE DRAFT
→ AWAITING_HUMAN_APPROVAL
→ EXACT-HASH APPROVAL
→ BUILT-IN CRM INBOX
→ lead_decision_bundle_v1
→ VERIFIED DURABLE EVIDENCE
```

The local form is the only inbound channel. The built-in CRM inbox is the only
destination. External CRM APIs, booking APIs, real model providers, generic
workflow machinery, and multi-agent behavior are outside B001.

## Deterministic boundary

B001 uses a fixed deterministic extractor so the full proof is reproducible
offline. Model-provider integration is deferred; the later provider must
produce the same validated extraction schema and will never control state,
approval, destination writes, hashes, or evidence.

Canonical JSON uses UTF-8, sorted keys, compact separators, and excludes
incidental database values. Every meaningful object receives a SHA-256 over
its canonical bytes.

## Qualification schema v1

Required local-form fields:

- `name`
- `email`
- `company`
- `service_needed`
- `budget_usd`
- `timeline_days`
- `message`

Score is an integer from 0 to 100:

- Budget: 40 points at `>= 15000`, 30 at `>= 5000`, 20 at `>= 1500`, else 0.
- Timeline: 20 points at `<= 30` days, 10 at `<= 90`, else 0.
- Fit: 25 points when both company and service need are present, 10 when only
  service need is present, else 0.
- Contactability: 15 points for a syntactically valid email, else 0.

Decision tiers:

- `QUALIFIED`: score `>= 70`; next action `SCHEDULE_DISCOVERY_CALL`.
- `REVIEW`: score `40..69`; next action `HUMAN_REVIEW`.
- `DISQUALIFIED`: score `< 40`; next action `SEND_POLITE_DECLINE`.

The explanation is a deterministic list of reason codes and human-readable
sentences derived from those exact scoring branches. The response draft is a
deterministic template derived from the normalized lead and decision.

## State and authority

The B001 run states are:

```text
RECEIVED
→ NORMALIZED
→ EXTRACTED
→ QUALIFIED
→ AWAITING_HUMAN_APPROVAL
→ APPROVED
→ DESTINATION_COMMITTED
→ BUNDLE_MATERIALIZED
→ VERIFIED
→ COMPLETED
```

Only deterministic application code changes state. Approval records bind:

- `run_id`
- `candidate_sha256`
- `actor_id = LOCAL_OWNER`
- `decision = APPROVE`

Approval of any other hash is rejected. Before a valid approval, both the CRM
inbox and CAS contain no run output. Repeating approval/commit is idempotent and
cannot create a second CRM record.

## Persistence and artifact

Persistence is one SQLite database in WAL mode plus a filesystem SHA-256 CAS.
The database stores current state in `runs`, durable typed JSON in `documents`,
approvals in `approvals`, the built-in destination in `crm_inbox`, artifacts in
`artifacts`, append-only evidence in `evidence`, and append-only audit history
in `events`. Audit events are not event sourcing.

`lead_decision_bundle_v1` is canonical JSON containing the normalized lead,
extraction, decision, score, explanation, next action, response draft, approval
reference, destination reference, and all relevant hashes. Its bytes are stored
in CAS; the database stores its hash and CAS reference.

## Transactions and recovery

Each stage commits its document, evidence, event, and current state in one
SQLite transaction. The destination commit uses a uniqueness constraint on
`run_id`. CAS writes use a temporary file followed by atomic replacement; an
orphan CAS object cannot promote database state.

B001 has no asynchronous or external side effect, so a local queue is not
needed to prove this slice. The schema reserves no speculative queue API.
Queue/lease implementation begins only when a real asynchronous provider or
external destination is introduced.

On restart, verification loads the stored chain, recomputes every canonical
hash, verifies exact-hash approval, confirms exactly one CRM record, reads and
hashes CAS bytes, and checks required evidence types. It never trusts a stored
`VERIFIED` flag by itself.

## Security laws

- Lead content is data, never authority.
- The app accepts form values only; no user-supplied file paths or commands.
- No destination write occurs before exact-hash approval.
- No commercial commitment is made by B001.
- No success is reported without version-correct durable artifact verification.

## B001 proof gates

1. Fixed lead reaches `AWAITING_HUMAN_APPROVAL`.
2. CRM rows = 0 and artifacts = 0 before approval.
3. Wrong/stale hash approval is rejected with no side effect.
4. Exact-hash approval creates exactly one CRM row.
5. Repeating commit creates no duplicate.
6. `lead_decision_bundle_v1` exists in CAS and its hash matches.
7. Database close/reopen preserves exact IDs, hashes, state, and evidence.
8. Independent verifier returns `COMPLETED` only for the intact chain.
9. Tampering with the stored bundle causes verification failure.

## Deferred

Real LLM calls, external CRM, calendar booking, queue/leases, retries, full web
or desktop UI, EXE packaging, RBAC, SaaS, cloud sync, generic Factory UI, and
all non-evidence-backed expansion remain deferred.
